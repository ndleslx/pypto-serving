Qwen3-14B 接入详解
—— 以 Host 侧优化为主线（异步调度、异步 prepare / reclaim 等）

PyPTO Serving 是面向昇腾 NPU 的本地推理栈：Qwen3-14B 与 DeepSeek V4 通过 PyPTO 融合内核在其上 serving。本文基于当前主干代码，完整拆解 Qwen3-14B 从 checkpoint 到 OpenAI 兼容 API 的接入路径，并重点分析 host 侧为隐藏主机开销所做的异步化设计。

代码基线：main @ 9db7e20 模型：Qwen3-14B（bf16，≈14 B 参数） 平台：Ascend NPU（a2a3）· Simpler L3 worker 整理日期：2026-09-18

1 · 概述

一句话概括接入方式：Qwen3-14B 在 pypto-serving 中不是"逐层拼算子"，而是编译为三个全层融合（all-layer fused）PyPTO 内核——prefill、decode、topk 采样——由 host 侧引擎做连续批处理调度，经 Simpler L3 worker 派发到 AICore 执行。

整个栈分为两个进程、五个层次：

  • 引擎进程：HTTP 服务（OpenAI 兼容）、异步调度引擎（连续批处理 / 分块 prefill / 前缀缓存 / 抢占）、KV cache 元数据管理、增量 detokenize；
  • Worker 进程（每副本一个，spawn 启动、独占设备组）：Qwen 执行器与 runner、常驻共享内存 I/O 缓冲、权重与 KV 的设备驻留，以及把内核派发做成 prepare → dispatch → reclaim 三级流水线 的能力；
  • Simpler L3 DistributedWorker：fork 出的芯片 worker，承接编译产物并管理设备内存，是 host 与 AICore 之间的运行时边界。

Host 侧优化的核心动机很直接：NPU 上单步内核执行很快，而每步之间 host 要做的事很多——调度器决策、构造批、写内核元数据缓冲、IPC 往返、采样回填、状态更新。如果这些串行排在内核执行前后，设备利用率与解码吞吐都会被主机拖垮。pypto-serving 的应对是把 host 工作全部"藏"到设备执行的时间窗里，本文第 4 章逐项展开。

阅读约定：文中 path/file.py:行号 均指当前主干代码位置，可直接检索定位。所有时序图/结构图为示意图，块宽度不代表实测耗时比例。

2 · 总体架构

两个对理解后文很关键的进程边界事实：

  • KV 页数由 worker 测算、engine 对齐：worker 在权重上载完成后按剩余显存算出页数，经 multiprocessing.Value 回传，engine 用它初始化 KvCacheManager 的块表（async_engine.py:269-287）。调度器从此只看元数据，不碰设备。
  • 共享内存必须先于 L3 worker fork 建立：fork 出的芯片 worker 只继承 fork 时刻的 host 内存，因此所有常驻 host 张量（权重 slab、TaskArgs 槽）都要先 share_memory_() 再创建 worker（buffer_set.py:9-16；npu_runner.py:163-168 的注释同样强调该顺序）。这条顺序被写成了硬校验：resolve_l3_arg 拒绝任何非共享的 CPU 张量。

3 · Qwen3-14B 模型接入

3.1 模型识别与执行器选择

CLI 读取模型目录的 config.json 做家族探测：model_type == "deepseek_v4"（或架构名匹配）走 DeepSeek，其余一律落入 qwen 家族（cli/main.py:494-505），映射到执行器类名 "PyptoQwen14BExecutor"（cli/main.py:508-512），经 EngineConfig.executor_cls 传给 worker；worker 进程内再解析为 Qwen314BPyptoExecutor（serving_worker.py:195-206）。

checkpoint 侧由 HuggingFaceDirectoryLoader 接管（model_loader.py:236-308）：解析 config.json 的形状字段（hidden_size、注意力头数、head_dim、vocab、层数、rope_theta、rms_norm_eps 等），构建 tokenizer，读取 model.safetensors.index.json 得到 weight_map。逐层权重此时只读元数据——weight_map 存入 RuntimeModel.extra，供执行器 staging 时按名惰性读取（model_loader.py:295-298）；真正 eager 读入的只有三个全局张量：embedding、final norm、lm_head（缺省时 tied 回 embedding），因为请求期的 embedding 查表需要它们留在 host 侧（model_loader.py:261-287）。

3.2 模型规格与 kernel 契约

Qwen3-14B 的内核是按这一精确形状编译的，executor 在编译期做硬校验（npu_executor.py:459-486），任何不匹配直接报错而不是静默出错：

三个内核（pypto-lib models/qwen3_14b/，经 PYPTO_LIB_ROOT 或仓库内 submodule 定位，npu_executor.py:72-118）：

  • prefill_fwd：一次派发跑完 40 层 prefill + LM head，按 block_table / slot_mapping 把 KV 直接写进分页池；输出 [batch, padded_vocab] 的 float32 logits（host 共享槽）。
  • decode_fwd：一次派发跑完 40 层 decode + LM head，PAGED 寻址与 prefill 共用同一设备驻留 KV 池，无需任何连续缓冲桥接；定批内核，运行时批从 seq_lens 描述符读出（npu_runner.py:618-633 的路径说明）。
  • topk_select_fwd：共享的 greedy / Top-K 选择器，sampling_control = [actual_batch, selection_k] 控制实际批与选择宽度（greedy 时 selection_k=1，Top-K 时为 32），同一程序复用而不额外注册 worker 程序（npu_runner.py:749-768）。

3.3 内核编译与磁盘缓存

KernelCompiler（common/compiler/compiler.py）把 pypto-lib 的 host wrapper（qwen3_prefill_host / qwen3_decode_host / qwen3_topk_select_host）编译为 DistributedCompiledProgram。编译走签名模式：张量形状 / dtype 从 wrapper 的注解读取，不需要传样例张量（compiler.py:76-83）。产物包装成 L3Callable（compiled 程序 + aicpu_thread_num + 可选 dispatch_args 前缀，l3_callable.py:17-35）。

打开 --use-compile-cache 后，每个内核直接落到 <build_dir>/<name>，下次启动凭 distributed_meta.json 命中即从磁盘重载，跳过 JIT 与设备编译；缓存按内核名分槽、不做指纹校验，调用方需保证目录与当前配置/内核源匹配（compiler.py:44-53, 103-140）。每个 worker 进程还有独立 build 目录 PYPTO_PROG_BUILD_DIR/serving_dp<rank>_d<devices>，避免多 worker 互踩（serving_worker.py:208-214）。

3.4 权重加载与分层 staging

融合内核按"整模型 slab"消费权重：每类权重是一块把 40 层沿轴 0 背靠背堆叠的张量。staging 由通用流水线完成（common/weights/），Qwen 只提供一张规则表（model/qwen/weight_spec.py:56-89）：

  • 投影矩阵（q/k/v/o/gate/up/down）：transpose=True 转成 [in, out]，cast bf16 —— cast 直接搭在 destination.copy_() 里完成；
  • norm gamma（input/post rms）：cast float32、flatten_to_row 成 [1, N] 行以便跨层堆叠；
  • QK norm 缺省：DefaultedWeightRule，缺失时按 [1, 128] 填 ones（不是 zeros——零会把缩放后的激活直接消灭，这是支持无 QK norm 变体的正确姿势）；
  • 全局权重：embedding 以零 pad 到 152064（pad id 永不被查表），lm_head 以复制第 0 行的方式 pad（零行会让 pad 词元拿到同一个有限 logit，变成采样噪声；weight-staging.md 记录了这条设计约束）。
stacked slab（40 层，轴 0）形状dtype
decode_wq / decode_wo[204800, 5120]bf16

decode_w_gate / decode_w_up[204800, 17408]bf16

性能与内存上的三个要点：

  • 峰值 host 内存 ≈ 1×：逐层读取——每层原始张量读出、写进自己的 slab 切片、随即释放，全程不 torch.cat（slab 一次性分配，后续层拿到的是自己切片的 view）。对比旧的"整包读入"路径（state dict + cast 副本 + 目的地同时存活），内存减半以上。
  • staging 线程池：14B 的逐层拷贝串行约 90 s，是启动主导项；各层写不相交的 slab 切片且 copy_ 释放 GIL，因此用线程池真并行。线程数默认 min(层数, CPU 数, 32)（内存带宽瓶颈，16-32 线程后不再增益），可用 PYPTO_STAGING_THREADS 覆盖；池外全局 torch.set_num_threads(1) 一次性钉住（per-worker 保存/恢复会竞态），否则 N 个 staging 线程各自展开 torch 线程池反而更慢（npu_executor.py:344-413；pipeline.py:66-91）。
  • slab 必须在共享内存：上传发生在 fork 出的子 worker 里，私有页对它是不可见的——这是正确性问题而非性能问题，所以分配器固定 torch.empty(...).share_memory_()（npu_executor.py:411）。

3.5 KV Cache 初始化：vLLM 式显存测算

init_kv_cache（npu_runner.py:204-262）的顺序本身就是一次优化——先让所有竞争显存的常驻物就位，再用剩余空间测 KV：

  1. 创建 L3 worker（此时 slab / TaskArgs 已在共享内存里）；
  2. 上传静态张量（权重、rope 表、final norm），并提前保留设备驻留的 decode 采样 scratch（~10 MB），保证它计入后续测算的峰值而不是首次 greedy 步才冒出来吃掉安全余量（npu_runner.py:228-236）；
  3. warmup 派发：按服务满配（max_batch_size × max_num_batched_tokens）跑一遍真规格的 prefill + decode，用 slot_mapping=-1 让全部读写落到 1 页 scratch 上——simpler 的 ring-heap arena 由此分配，且超配的 max_num_batched_tokens（会顶到融合 prefill 的单芯 attention 堆上限）在启动期就暴露，而不是等第一个请求（npu_runner.py:442-515）；
  4. 测算页数：pages = (total × utilization − max(peak_non_kv, simpler_committed)) / bytes_per_page，其中 peak_non_kv = total − free 由驱动口径读出，simpler_committed 是 simpler 内存分配器的权威总量，两者取 max 以防任一口径低估（npu_runner.py:322-361）；
  5. 失败减半重试：分配 OOM 则页数减半重试，下限 max_batch_size 页（npu_runner.py:264-297）；
  6. 页数回传 engine 初始化块表，并打印逐项内存构成（权重估算 / KV 精确 / arena / 残差，npu_runner.py:363-436）。

按 bf16、页 128 token 计，每页 KV = 40 层 × 2(K/V) × 8 头 × 128 位置 × 128 维 × 2 B ≈ 20 MiB。以 64 GB HBM、0.90 利用率、权重约 28 GB 为例做示意估算：KV 预算 ≈ 57.6 − 28 − arena ≈ 28 GB，约 1400 页 ≈ 18 万 token 的上下文容量。

3.6 Prefill 执行路径

调度器把若干请求的 prefill chunk（可能来自不同请求、不同 chunk 起点）合成一个 PrefillBatch：所有 chunk 的 token 拼成一个设备张量，chunk_offsets 记录各 chunk 在拼接张量里的位置，chunk_starts 记录各 chunk 在各自序列里的绝对位置（RoPE 用，serving/utils/prefill.py:35-64）。runner 把它们写进常驻缓冲（§4.5），逐请求写 block_table 行与 slot_mapping（物理槽 = page_id × page_size + 页内偏移，跨页用 np.arange 连续段直写 numpy 视图，npu_runner.py:1082-1114），然后一次 _run_l3 派发 prefill_fwd。

采样只发生在完成 prompt 的末 chunk 上：greedy（temperature ≤ 0）直接用设备端 topk_select(k=1) 的结果；否则走 Top-K 候选或 host 采样（serving_worker.py:699-737）。

3.7 Decode 执行路径

decode_fwd 是定批内核：无论实际几个请求都计算全部 max_batch_size 行。补齐方式很讲究——把活跃行 0 的输入复制进 padding 行：这些行重算行 0 的 K/V 并写回行 0 自己的槽，是幂等写，绝不会污染别的请求的物理页；它们的 logits 随后裁掉（npu_runner.py:626-633, 1046-1054）。相比"padding 行指向独立 dummy 页"，这省掉了额外页占用与清理。

每步真正要写的 host 侧元数据只有三样：token_ids 首列、seq_lens、每行的 slot_mapping；block_table 行带缓存——某行的页分配没变就不重写（npu_runner.py:1061-1080），长连接 decode 稳态下基本零写入。

3.8 采样：设备端 greedy / Top-K

采样被尽量推到设备上，避免每步把全词表 logits 搬回 host：

  • greedy（temperature ≤ 0）：decode_fwd 直接产出 sampled_ids，host 只回读 [batch, 1] 个 int；全词表 logits 写入设备驻留 scratch，根本不落 host（npu_runner.py:812-834）。
  • Top-K 采样（temperature > 0 且 1 ≤ top_k ≤ 32）：设备端 topk_select_fwd 产出 top-32 的 (value, index) 候选，host 在 32 个候选上做温度采样（sampler 按 SamplingParams），传输量从 152064 × 4 B/行 降到 32 × 8 B/行。
  • host 兜底：不满足上述条件（如 top_k > 32 或需要完整 softmax）时回退 host 采样，此时才回传裁剪后的 logits。

4.2 异步调度：引擎级 depth-2 流水线

4.2.1 动机

同步模式下（async_scheduling=False，或旧版行为）每个调度步是严格的一问一答：

engine: schedule() → 编码 StepCommand → IPC → 阻塞等结果 → update_from_output() → 下一步
worker:              解码 → 准备输入 → 派发内核 → 等内核完成 → 回收 → 编码 StepResult → IPC

设备执行内核期间，引擎进程闲着；引擎调度与更新期间，设备闲着。解码步内核本身只有几十毫秒量级，而调度器决策 + 批构造 + IPC 往返 + 状态更新合计可达毫秒到十毫秒级——这些主机时间每步都全额出现在关键路径上。

4.2.2 引擎循环：派发不等待，等待只发生在队列满时

开启异步调度后（EngineConfig.resolve_async_scheduling() 默认返回 True，对所有执行器生效，async_engine.py:93-99；当前无 CLI 开关），引擎维护一个深度为 2 的在飞行列 _batch_queue（async_engine.py:218-224）：

while running:
    if len(batch_queue) < 2 and scheduler.has_work():
        dispatched = try_dispatch_step()        # schedule() + IPC，非阻塞
    if batch_queue:
        if len(batch_queue) >= 2 or not dispatched:
            await await_and_apply_oldest()       # 只在队列满/无事可派时阻塞取最老结果
    elif not dispatched:
        flush_pending_frees(); sleep(1 ms)

要点（async_engine.py:460-538）：

  • 派发完全非阻塞：StepCommand 编码后直接 input_queue.put()。step N 在设备上执行时，引擎已经在构造并投递 step N+1——worker 一做完 N 就能立刻取到 N+1，设备不再为引擎调度空转。
  • FIFO 对齐：worker 每条命令恰好回一条结果且按序，因此"最老在飞步骤"就是下一个到达的结果；引擎按 step_id 核对，错位即致命失步（async_engine.py:558-568）。
  • 深度选 2 而不是更深：一步的输入依赖上一步的采样 token（见下），更深需要更复杂的 token 链推导，收益却递减；深度 2 已足够把引擎侧 host 工作全部藏进设备执行窗。

4.2.3 乐观状态推进与占位 token：跨步一致性的两根支柱

depth-2 的难点在于：调度 step N+1 时，step N 的采样 token 还没回来，但调度器看到的状态必须"像已经拿到 token 一样"自洽，否则同一个槽位会被重复调度。解决方案是一对配套机制：

① 乐观推进（advance_after_schedule，scheduler.py:554-611）。派发后立刻按"这步会成功"推进状态：

  • num_computed_tokens += num_new_tokens（本步覆盖的 token 视为已算，镜像同步路径 update_from_output 的行为）；
  • 会采样的步骤（decode 或完成 prompt 的末 prefill chunk）为输出预留 num_output_placeholders：投机/MTP 解码按上界预留 1 + num_speculative_tokens，因为实际接收数只有 worker 回复后才知道；占位计入 num_tokens（scheduler.py:105-114），使 num_new_tokens_needed / is_prefill 在下一步 schedule 时保持正确；
  • 前缀缓存发布被显式推迟到结果确认后：派发时 KV 尚未真正写入，此时发布块哈希，一旦该步失败/超时，后续同 prompt 请求会命中"未算却已发布"的块——发布统一挪到对账阶段（scheduler.py:589-593）；
  • terminal prefill 栅栏：完成 prompt 的 prefill 步在 worker 确认并初始化好请求级 decode 状态前，该请求不再被派发为 decode（terminal_prefill_in_flight，scheduler.py:99-103）——栅栏是每请求粒度，无关请求继续走 depth-2 流水。

② 占位 token（PLACEHOLDER_TOKEN = -1，ipc.py:35）。step N+1 的 decode 输入 token 在命令构造时未知（async_engine.py:663-673）：

engine 构造 step N+1last_token 尚未知 → 发送 -1→ worker FIFO 保证运行 N+1 时 N 的结果必已采样并缓存→ _resolve_decode_tokenserving_worker.py:739-753从 _last_tokens[req] 取最近一枚回填

seq_len 同样在 schedule 时刻快照（num_computed + num_new），不能使用含其他步占位的 num_tokens——否则位置会错位，这在 chunked prefill + 深度 2 下真实出现过（重复/错位 token，async_engine.py:676-684 注释）。

4.2.4 结果对账与一致性（_reconcile_async_output）

结果到达时（scheduler.py:718-808）：释放本步预留的占位 → 此刻才发布前缀缓存块（且按本步快照的物理表发布，而非请求当前滚动表——更新的在飞 chunk 可能已推进过表）→ 追加真实 token、产出流式输出。投机解码的未用余量回退：预留上界减去实际保留 token 数，差额从 num_computed_tokens 扣回，最终账目与同步路径逐 token 一致（scheduler.py:793-808）。

三类边界都有明确处置：

  • 请求已结束/被抢占但还有在飞步骤：结果直接丢弃（其块已释放或状态已重置，再应用会损坏账目）。抢占路径同时清零占位与栅栏，请求回到 waiting 干净重排（scheduler.py:639-649, 919-923）。注释里记录了深度 2 下该检查的正确性边界：更深的流水需要改为每请求调度纪元。
  • 步骤出错 / 超时（async_engine.py:742-788）：失败批及其所有依赖其乐观状态的在飞批全部作废、请求中止；由于 worker 仍会对每条命令回一条结果，作废步骤的 step_id 记入 _discard_result_step_ids，由 _get_live_result 在取结果时排空丢弃，保证陈旧结果永远不会被张冠李戴到后续批次上（async_engine.py:588-604）。
  • 空闲期的清理：无活可干但有待释放请求时，发一条空批 clean-up StepCommand（只带 finished_request_ids），worker 容忍空批并回空结果，避免中止请求的设备槽被钉住（async_engine.py:701-740）。

4.2.6 时序对比

4.3 Worker 三级流水线：异步 prepare / dispatch / reclaim

4.3.1 设计问题

引擎级流水（模式 B）解决了"引擎侧"的主机开销，但 worker 进程内部仍是串行的：准备输入 → 派发并等待内核 → 回收输出。其中"准备输入"（写内核元数据、构造张量描述）与"回收输出"（等待完成、读采样结果、编码 StepResult）都是 host 工作，且都不需要占用设备。把它们拆成独立车道，就能与设备执行重叠——这是模式 C。

4.3.2 三车道结构

worker 的 _pipelined_busy_loop（serving_worker.py:252-338）把执行拆成三条 FIFO 车道、两个内部队列：

4.3.3 prepare：设备忙时就把元数据备好

_prepare_step_command（serving_worker.py:755-796）只处理"纯 decode、无新请求"的命令，且要求执行器支持设备端 decode embedding（否则占位 token 无法正确嵌入，保留串行路径）。它调用 runner 的 prepare_decode(runtime_model, batch, buffer_slot=…)，把 batch 的请求集合、seq_len、块表等一切不依赖上一步输出的信息固化成快照；token 字段留占位。能力协议由 ModelExecutor 基类定义（executor.py:66-122），PyptoExecutor 转发到 runner 并声明 supports_async_decode_prepare（pypto_executor.py:128-172）——worker 主线程可以在 device 线程执行的同时调用 prepare，实现必须在没有锁保护的情况下保持对正在执行的 decode 不可见。

4.3.4 dispatch：late-bind 与异步提交

device 车道拿到快照后（serving_worker.py:373-406）：若执行器声明"dispatch 仍需要上一步 token"（prepared_decode_requires_token，默认 True），先 late-bind——从 _last_tokens 解析占位 token、重建 token_ids 张量、替换进快照的 batch（_late_bind_prepared_decode_batch，serving_worker.py:483-502）；然后 dispatch_prepared_decode 走 _submit_l3：解析参数 → worker.submit() → 立刻返回 PendingL3Dispatch（l3_dispatch.py:135-175）。每步临时上传的张量所有权移交 pending 句柄，等 wait() 回收输出时统一释放（l3_dispatch.py:52-78）。DeepSeek fused-MTP 的实现则连 token 都不需要 late-bind——其持久设备状态在 prefill 期已定，冷/热描述符一律原样提交（npu_runner.py(deepseek):1132-1138）。

4.3.5 双缓冲槽乒乓

流水线中相邻两步的输出缓冲会同时存活（一步在写、一步在读），因此每类 decode I/O 需要两份。机制（serving_worker.py:52, 260-333, 443-444）：

  • 槽号 = step_id % _DECODE_PIPELINE_SLOTS（=2），随命令传入 prepare_decode(buffer_slot=…)，由 runner 选用对应的缓冲组；
  • 每槽一把 Semaphore(1)：主线程在 prepare 前 acquire，reclaim 车道发布结果后 release——同一槽的复用被硬性互斥，prepare 永不会覆盖尚未回收的输出；
  • 串行回退路径（无槽命令）不持有信号量，buffer_slot 仅用于错误回执。

4.3.6 顺序与生命周期保证

  • 释放先于注册的快照：主线程在发布新注册前，先快照 finished_request_ids 对应的缓存条目；device 车道应用释放时逐条比对"当前条目还是快照那个对象"才删——防止释放一个已被同 ID 新请求复用的条目（serving_worker.py:298-309, 547-579）。
  • 生命周期留在 FIFO device 车道：请求释放/注册与设备工作同序应用，顺序语义与串行循环完全一致。
  • profiling 屏障：ProfileCommand 作为屏障插入输出队列，device 车道等它执行完才继续——保证 profiler 的启停与输出回收有序（serving_worker.py:91-94, 356-360, 429-434）。
  • 什么走串行回退：prefill 命令、带新注册的命令、prepare 失败、执行器不支持 split——统一落到原来的同步路径，正确性优先（_can_split_decode_output，serving_worker.py:447-462）。

4.3.7 接入条件与当前状态（重要）

能力开关在 runner 手里。worker 进入三车道循环的条件是 executor.supports_async_decode_prepare（busy_loop 分岔，serving_worker.py:216-225），而它要求每个注册的 runner 都实现 prepare_decode / run_prepared_decode（pypto_executor.py:128-135）；独立 dispatch/reclaim 回收再要求 supports_async_decode_reclaim + dispatch_prepared_decode / reclaim_prepared_decode（pypto_executor.py:174-182）。

当前主干状态：该框架由 DeepSeek V4 fused-MTP runner 完整接入并验证（deepseek/npu_runner.py:1651-1773；提交 1aed42d / b1c19a3）；Qwen3-14B runner 尚未实现 runner 级 split 接口，因此 Qwen 的 worker 运行 FIFO 串行循环——但依然完整受益于 §4.2 的引擎级 depth-2 异步调度与占位 token 机制（串行循环同样执行 _resolve_decode_token 回填），即图 2 的模式 B。

Qwen 接入路径（框架已备好，无需改 worker）：在 Qwen314BModelRunner 上实现四个方法——prepare_decode（复用 _prepare_decode_inputs 的元数据写入，token 留占位、按 buffer_slot 选择缓冲组）、dispatch_prepared_decode（走 _submit_l3 异步提交）、reclaim_prepared_decode（等 pending、读 sampled_ids/topk 槽）、run_prepared_decode（dispatch+reclaim 串行组合，供回退路径）；并把 decode 的输出槽（sampled_ids、topk 值/索引）双份化以配合槽乒乓。Qwen 属于"dispatch 需要 token"的类型，late-bind 通道（§4.3.4）就是为它准备的。

4.4 轻量化 IPC 协议

引擎与 worker 之间的命令是 msgpack 编码的增量协议（ipc.py:10-23）：prompt 与采样参数经 NewRequestData 每请求只发一次，worker 端 _req_cache 记住；此后每步只传增量（每请求一个 DecodeRequest，batch 16 时整条命令约 1 KB），对比旧的全图 pickle 每步约 160 KB，序列化与跨进程拷贝开销降两个数量级。结构一览：

消息方向关键字段
StepCommandengine → workernew_requests（首见请求）/ prefill_requests（chunk_tokens、num_computed_tokens、block_ids）/ decode_requests（last_token 可为 -1 占位、schedule 时刻快照的 seq_len、block_ids）/ finished_request_ids / 单调 step_id
StepResultworker → enginenew_tokens: {request_id: [token…]}（MTP 为多 token）、error、回显 step_id
ShutdownCommand / ProfileCommandengine → worker退出循环 / 启停进程内 SA profiler（确认走独立队列，不与推理结果混淆）

4.5 常驻共享内存缓冲（TaskArgs）

runner 为每类派发（prefill / decode / topk）维护一个 TaskArgs：以内核位置参数顺序注册所有参数——I/O 槽（host 共享内存张量）、静态权重（StaticDeviceTensor 标记，上传一次后缓存）、KV 池句柄（lazy source，build 时解析）（qwen/task_args.py:107-205）。热路径收益：

  • 零每步分配：所有定形缓冲（seq_lens、block_table、slot_mapping、logits、token_ids、sampled_ids、topk 输出……）构造期一次 torch.empty(...).share_memory_()，此后原地复写；元数据用 numpy 视图直写（npu_runner.py:183-191）；
  • 静态权重一次上传：resolve_l3_arg 以 (data_ptr, shape, dtype) 为缓存键，命中直接复用设备指针，全 40 层权重与 rope 表在服务期内只进设备一次（buffer_set.py:88-136）；
  • 每次派发的元组也可缓存：槽在原地写、句柄稳定，build(use_cache=True) 免去重复构造（task_args.py:191-210）；
  • 顺序即契约：注册顺序就是内核签名顺序，文件本身即位置契约的单一事实来源，杜绝"改了内核签名忘改调用方"。

此外 prefill 的 input_ids / slot_mapping 以按调用长度的切片拼接进已构建元组（npu_runner.py:770-781），decode 在设备采样时把 logits / next_hidden 换成设备驻留 scratch（npu_runner.py:783-796）——都是"常驻缓冲 + 少量拼接"的同一思想的延伸。

4.6 设备端 embedding 与采样

Qwen 执行器声明 supports_device_embedding（prefill 与 decode 都在内核内查表，engine 无需先算 hidden states，npu_executor.py:165-168）与设备采样能力（§3.8）。组合效果：稳态 greedy decode 每步跨 host/device 边界的只有——输入侧一个 int token id，输出侧一个 int 采样 token；全词表 logits（16 × 152064 × 4 B ≈ 9.7 MB/步 @batch16）全程留在设备。Top-K 采样把边界流量限制在 32 个候选对。这是 host 侧优化里"把工作移回设备"而非"重叠工作"的一条线。

4.7 其他 host 侧优化

  • 增量 detokenize：只 decode 新完成的文本窗口（保留 3 token 前缀窗口防多字节字符跨界损坏），每步 O(1) 摊销，替代每步全量 re-decode 的 O(N²)；结束时一次性全量 decode 兜底未完成的多字节尾字符（async_engine.py:846-896）。
  • 非流式 final-only 输出：非流式请求中间 token 不入队，每请求一次 queue push / 一次协程唤醒，替代每 token 一次（async_engine.py:120-126, 826-829）；stop string 检测仍每步执行，只是发布被推迟。
  • gc.freeze() 冻结常驻集：引擎与 worker 各自在常驻集就绪后 collect(0/1/2) + freeze()，把权重、编译内核、KV 块对象提升为永久代，gen2 不再重扫——避免毫秒级 GC 停顿插入解码步中期（gc_utils.py:34-45；async_engine.py:293、serving_worker.py:986-991，两进程各自执行，freeze 不跨 spawn）。
  • 调度器本身的开销控制：连续批处理 + chunked prefill（长 prompt 切 ≤2048 token 的 chunk，与 decode 混步）+ vLLM 式抢占（块不足时按到达时间抢最低优先级受害者，回炉重算）+ 链式哈希前缀缓存（块哈希含父块哈希，命中即整前缀匹配；命中保留最后 1 token 不缓存，保证首 token 走与冷启动相同的内核路径，kv_cache.py:27-29, 393-415）。
  • 启动路径：权重 staging 线程池 + 磁盘内核缓存（§3.3/3.4）把重启成本压到"读 slab + 重载编译产物"。
